# Standards-informed Zero Trust Policy Design for EV Charging

This repository provides the policy specifications, source-evidence register, annotated corpus, and model artifacts associated with the research article **Standards-informed Zero Trust Policy Design for EV Charging: Conditional Predicates, Enforcement Boundaries and Model-based Feasibility**. It supports four conditional policy specifications and a model-based analysis of session processing and shared OCSP service capacity. The design specifies additional admission decisions, trusted attributes and candidate enforcement boundaries; it does not contain an implemented A1–A4 policy engine or attack-effectiveness evidence.

## Start here

1. Read [Policy_Design_Trace.xlsx](Policy_Design_Trace.xlsx) or [policy/policy_trace.json](policy/policy_trace.json) for the four patterns and 16 predicate records. These are design records, not executed test cases.
2. Resolve clause identifiers through [evidence/source_register.json](evidence/source_register.json) and [evidence/targeted_ocpp_evidence.json](evidence/targeted_ocpp_evidence.json). Obtain the cited standard editions for independent semantic review.
3. Read [Corpus data and field definitions](#corpus-data-and-field-definitions) for the mapping dataset and its field definitions.
4. Follow [Run the model](#run-the-model) to run the S1/OCSP model and interpret its saved numerical outputs.

## Policy interpretation

A1 checks the DSO input before CSMS translation. A2 admits an identified EMS/site/target input before applying existing OCPP profile and composite-limit rules. A3 assumes an enforceable station-internal software boundary whose implementation is not demonstrated. A4 separates access admission from OCPP session protection and identifies optional hardening. The expired-certificate recovery exception is limited to its stated configuration and does not prescribe P2.

SC.01 composition and OCPP profile priority are existing baseline behavior. An external cap is not an immediate setpoint. A stricter cap-admission rule is optional deployment policy, not proof of an attack that baseline composition would fail to constrain.

The model evaluates session-processing delay, fleet-size sensitivity, concurrent OCSP requests, responder capacity and processing-input sensitivity under stated assumptions. The input documentation and output mappings are in [model/model_inputs.json](model/model_inputs.json) and [model/model_result_map.json](model/model_result_map.json). Pooled session percentiles and full histograms cannot be reconstructed from seed means alone because individual session observations are not archived.

## Corpus data and field definitions

`corpus/requirement_master_1553.csv` contains the author-annotated mappings supplied with this study. It contains 1,553 mapping instances and 1,293 unique (Standard, Requirement ID) items. Items include requirements, controls and recommendations; the counts are not uniformly mandatory obligations, security strength scores or absence findings.

The rows identify analytical placements and do not establish every policy interpretation or all direct network adjacencies. The five-source counts are NIST 60 unique/212 mapped, ISO 871/966, OCPP 229/230, ENISA 82/94 and IEC 51/51. `corpus/architecture.json` supplies the ten logical entities, grouping and inter-group rule for 39 screening pairs. This file defines a reference frame, not a deployed topology.

The exact initial OCPP extraction file is not conclusively identified. `evidence/source_register.json` separately identifies the Edition 4 documents used for the policy specifications. Shared requirement identifiers do not prove edition identity or semantic equivalence. Full standards text is not redistributed.

### Reading the CSV

The CSV has one header row and 1,553 data rows. Each row is one annotated mapping instance. `Mapping ID` is unique within this file. A source item is identified by the composite key `(Standard, Requirement ID)`; the same source item can therefore appear in several mapping rows. Count rows to obtain 1,553 mappings and count distinct composite keys to obtain 1,293 source items. Do not sum `Mapped_Count` to obtain either total.

| Column | Meaning in this artifact |
| --- | --- |
| `Type` | Analytical placement category: `Node`, `Edge`, `Organization Policy`, or `IEC Cross-cutting`. |
| `Mapping ID` | Preserved unique row identifier. Identifier gaps are not evidence that rows are missing from this supplied source extract. |
| `Zone_Area` | Annotated zone, cross-zone relation, organizational scope, or cross-cutting scope. |
| `Entity` | Annotated logical entity. For `Edge` rows, it is the two endpoint labels joined by `\|`. `ORG` and `IEC 62443` denote non-endpoint categories. |
| `Sub Entity` | Node-level subentity annotation; blank for the other three placement categories. |
| `Endpoint A`, `Endpoint B` | Logical endpoint labels for `Edge` rows; blank for the other categories. These analytical labels do not establish a direct operational connection. |
| `Edge Label` | Preserved relationship label for `Edge` rows; blank for the other categories. |
| `Document` | Source-document label inherited from the annotated dataset. Some labels are abbreviated and do not independently identify the exact source edition or extraction file. |
| `Standard` | Source-family key: `NIST`, `ISO`, `OCPP`, `ENISA`, or `IEC`. |
| `Requirement ID` | Source item identifier. These items have differing normative force and include controls and recommendations as well as requirements. |
| `Source_Area` | Inherited source-area or locator annotation. This field is sparse: it is blank in 812 Node rows, all 446 Edge rows and all 51 IEC Cross-cutting rows. A blank does not establish the absence of a source item. |
| `Mapped_Count` | Repeated placement-group size for Node/Edge rows. In this file, each nonblank value equals the number of rows with the same `(Type, Zone_Area, Entity, Sub Entity)` values. It is blank for Organization Policy and IEC Cross-cutting rows. Summing the repeated values gives 156,735 and is not a source-item or mapping-instance total. |

The placement categories contain 941 Node rows, 446 Edge rows, 115 Organization Policy rows and 51 IEC Cross-cutting rows. The endpoint fields are populated only for Edge rows. Empty cells retain the representation used in the supplied dataset.

## Run the model

The default configuration uses 100 seeds (0–99), a 7,200-second session-simulation horizon, and fleet sizes of 50, 100, 500 and 1,000 EVSEs. The separate burst routine processes each batch to completion. Importing the script also starts execution, because its analysis runs at module top level.

Python 3.11 or later is required by the pinned NumPy version. Install the dependencies in a separate Python environment using that interpreter. The following commands assume `python3` meets this requirement and are run from the repository root in a POSIX shell:

```sh
python3 -m venv /tmp/ev-policy-model-env
. /tmp/ev-policy-model-env/bin/activate
python3 -m pip install -r model/requirements.txt
unset ZTA_QUICK
ZTA_RESULTS_DIR=/tmp/ev-policy-model-reproduction ZTA_NO_FIGURES=1 python3 model/simulation_code.py
```

| Environment variable | Behavior |
| --- | --- |
| `ZTA_RESULTS_DIR` | Output directory; defaults to `model/results/` |
| `ZTA_NO_FIGURES=1` | Suppresses image export without changing numerical computation |
| `ZTA_QUICK=1` | Uses 3 seeds, a 300-second session horizon, and fleet/burst sweep sizes of 10 and 20 EVSEs; the default-fleet and input-sensitivity analyses still use 50 EVSEs |

Use the default configuration to compare with the supplied results. Directing output to a separate directory preserves those reference files. The script writes four numerical files: `simulation_summary.json`, `per_seed_results.csv`, `ocsp_capacity_sweep.csv`, and `input_sensitivity.csv`. The output CSV already contains only the S1-related scenarios; no additional scenario filtering is needed.

To generate the three model figures as well, keep the separate output directory and set `ZTA_NO_FIGURES=0` or leave that variable unset. The generated filenames are `overhead.png`, `evse_sensitivity.png`, and `burst.png`, corresponding to Figures 2, 3 and 4. The supplied manuscript figures are stored in `figures/`; see the [figure mapping](#figures). Running the script does not update those files, this README or the model metadata automatically, and it does not remove older files from the output directory.

For numerical comparison, use the matching scenarios, configurations, metrics and seeds in `per_seed_results.csv`, the summary fields listed in [model/model_result_map.json](model/model_result_map.json), and the capacity/input-sensitivity CSV files. Numerical equality across different Python or library versions is not guaranteed.

## Model interpretation and data limits

The S1 point estimate and tail percentiles are pooled session statistics. The confidence interval resamples 100 seed means with 2,000 bootstrap draws. Fleet means and sample standard deviations use the seed means. Burst means and percentiles pool OCSP requests; a pooled percentile is not the average of per-seed percentiles. The saved outputs contain seed summaries and pooled summary statistics, not every session sample. Consequently, the pooled tails and full histogram cannot be reconstructed from seed means alone without re-executing the model. The input-sensitivity CSV contains rounded summaries; its per-seed input-sweep means are not archived.

All processing distributions, responder capacities, reconnect timings and burst fractions are assumptions. The modeled OCSP time includes service and queueing after request submission. The 30-second message timeout is used for contextual comparison; the routines do not enforce a timeout. The model does not simulate a heartbeat schedule. mTLS normal draws have a lower bound of 10 ms and OCSP normal draws have a lower bound of 1 ms, as recorded in `model/model_inputs.json`.

`burst_ocsp_capacity_sweep[*].queueing_share_pct` is calculated as `(mean_ms - 20.0) / mean_ms * 100`, where 20.0 ms is the configured nominal OCSP service mean. The numerator is an inferred queueing component, not a separately archived service/wait observation. The model does not retain separate per-request service and waiting times. At low load this proxy can be slightly negative because the sampled service mean differs from its nominal mean; it is not a measured negative waiting time. The 1,000-EVSE/capacity-eight value gives approximately 96.4% by this nominal-service approximation.
